# Performance assessment via Claude Code (read-only)

> **Paper trading only.** This runbook only ever *reads* `state/` and reasons about it. It never submits orders, never edits `state/`, never restarts services, and never applies fixes automatically. Any change Claude proposes comes back as a diff for you to review. See [CLAUDE.md §Promotion to live](../CLAUDE.md#promotion-to-live-documented-only--do-not-enable-in-code).

The idea: let Claude Code assess how the paper account is doing from its own logs, judge it against the build spec's promotion gates, and suggest fixes — without inventing the numbers each time. A deterministic script (`bin/assess_performance.py`) computes the statistics; Claude interprets them.

Why deterministic-script-then-Claude, not Claude-eyeballs-the-logs: the arithmetic (Sharpe, drawdown, win-rate by factor, cost drift) must be computed the same way every run or week-over-week comparisons are meaningless. The script pins the math (reusing the same functions the dashboard uses); Claude adds the judgment.

| Step | What runs | Writes? |
|---|---|---|
| 1. Generate numbers | `bin/assess_performance.py` | Only the `--json` file you name |
| 2. Assess | Claude Code, reading that output | Nothing (proposes a diff for review) |

## Prerequisites

The VPS is already set up per [deploy/README.md](README.md) (repo at `/opt/agent-trading`, project-local `.venv`, `state/` populated by real cycles). Claude Code CLI installed on the box — see [code.claude.com/docs](https://code.claude.com/docs).

Run Claude Code **on the VPS**, in the repo directory, rather than SSHing the data to your laptop: the code and the logs live together there, so nothing has to be copied.

## Step 1 — generate the numbers (read-only)

```bash
ssh <you>@<your-vps>
cd /opt/agent-trading
sudo -u agent .venv/bin/python -m bin.assess_performance --json state/assessment_latest.json
```

This prints a Markdown report to stdout and also writes the machine-readable
version to `state/assessment_latest.json` (gitignored). The report is organised
around the CLAUDE.md §Promotion gates and carries the sample size (N) next to
every statistic, plus a **LOW SAMPLE** banner when there is too little history
to draw conclusions.

Flags:

| Flag | Effect |
|---|---|
| `--json PATH` | Also write the machine-readable assessment dict to `PATH`. |
| `--limit N` | Only the most-recent N cycles in the timeline table (default: all). |

The script is strictly read-only apart from the `--json` file it writes. It reads
`state/*.jsonl` and `state/runs/`, computes, and formats — no broker calls, no
`state/` mutation, no secrets in the output.

## Step 2 — the assessment prompt

Launch Claude Code in the repo dir:

```bash
cd /opt/agent-trading
sudo -u agent claude
```

Then paste a prompt like this (adjust freely — the guardrails are the part to keep):

> You are assessing this paper-trading system's performance. **Read-only mandate:
> do not edit `state/`, do not restart services, do not run the order path, do not
> submit anything to the broker.** Never print API keys or `.env` contents.
>
> 1. Read `state/assessment_latest.json` (generated by `bin/assess_performance.py`)
>    and, if useful, `bin/analyze_runs.py` output.
> 2. Judge the numbers against `CLAUDE.md` §Promotion to live and §System scope —
>    where does actual behaviour diverge from the spec's intent?
> 3. **Treat any finding on low sample as directional, not actionable.** If the
>    report shows the LOW SAMPLE banner, or a metric's N is small, say so and do
>    not recommend tuning prompts to it — a few weeks on a $2,500 account is mostly
>    variance.
> 4. Output your assessment as prose, and any suggested code/prompt changes as a
>    **diff or PR for me to review** — do not apply them. Note that `prompts/*.md`
>    are prompt-cached and deliberately byte-stable across paper→live, so flag the
>    cache/continuity cost of any prompt edit.

### Guardrails (why they matter)

| Guardrail | Reason |
|---|---|
| Read-only, no `state/` writes | The logs are append-only history; a stray write corrupts P&L / cooldown / the Sharpe gate. |
| Don't restart services / run the order path | An assessment must never interrupt a live cycle or place a trade. |
| Flag low-N as directional | Prevents over-fitting prompt changes to noise — the main failure mode here. |
| Fixes as a reviewable diff, never applied | Keeps a human in the loop, consistent with the triple-lock, paper-only design. |
| Never echo secrets | Claude runs with the real `.env` in scope; the report/diff must stay key-free. |

If you need to stop everything mid-assessment, the halt procedure is unchanged:
`sudo -u agent touch /opt/agent-trading/state/halt.flag` (every systemd unit
refuses to start while it exists).

## Optional — a weekly assessment on a timer (documented, not installed)

If you want `state/assessment_latest.json` refreshed automatically so Claude always
has fresh material, add a sixth systemd unit following the existing three-part
timer shape (`deploy/systemd/`). This is **not installed by default** — wiring it
in means editing `install.sh`'s unit list and the `tests/test_deploy*.py`
assertions, so treat the below as a sketch to adapt, not a drop-in.

`agent-assess.service` (oneshot):

```ini
[Unit]
Description=Agent-Trading weekly performance assessment (read-only)
ConditionPathExists=!{{REPO_DIR}}/state/halt.flag

[Service]
Type=oneshot
User={{USER}}
WorkingDirectory={{REPO_DIR}}
ExecStart={{REPO_DIR}}/.venv/bin/python -m bin.assess_performance --json {{REPO_DIR}}/state/assessment_latest.json
```

`agent-assess.timer`:

```ini
[Unit]
Description=Run the weekly performance assessment

[Timer]
OnCalendar=Mon *-*-* 12:00:00 UTC
Persistent=true
Unit=agent-assess.service

[Install]
WantedBy=timers.target
```

The timer only regenerates the numbers; the Claude interpretation step stays a
deliberate, human-initiated action (Step 2).
